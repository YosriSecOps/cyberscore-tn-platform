CyberScore TN — Architecture Technique & Orchestration Multi-Agents

De l'audit web au rapport de sécurité souverain : conception d'une plateforme unifiée conteneurisée sur hôte durci Red Hat Enterprise Linux (RHEL 9.5), pilotée par un graphe d'agents IA et un modèle LLM local (Ollama).

🛡️
Socle RHEL 9.5 Hardened
Hôte minimal d'entreprise sous VMware 17 Pro avec SELinux actif en mode Enforcing et Firewalld strict.
📦
Sandboxing Conteneurisé
8 conteneurs Docker cloisonnés (Nmap, Nuclei, Headless Browser) sans impact ni conflit sur l'OS hôte.
🧠
IA Locale Souveraine
Modèle Qwen local sous Ollama avec Function Calling (temp 0.1) garantissant zéro fuite de données d'audit.

Décomposition Détaillée des Composants du Schéma

🖥️ Frontend — Next.js 16.3 Turbopack & App Router
  • Interface utilisateur : Dashboard réactif trilingue (FR, AR RTL, EN) développé en TypeScript et Tailwind CSS.
  • Modes d'audit : Quick (~3s), Standard (~8s), Deep (~30s) et Audit Autonome Multi-Agents (IA).
  • Affichage temps réel : Timeline interactive des 4 agents animée en direct et streaming télémétrique.
  • Restitution certifiée : Matrice des faiblesses, grille des ports réels, roadmap copier-coller et sceau SHA-256.
⚙️ Backend & API Routes Orchestrateur Principal
  • API REST & Handlers : FastAPI (/api/v1) et Next.js route handler (/api/scan) pour le pilotage d'audit.
  • Sous-processus Sonde : Déclenchement de probe_agent.run avec flux JSON stdout et gestion UTF-8.
  • Gestion d'état : Maintenance de l'objet d'état partagé Pydantic AuditState.
  • Sécurité : Authentification JWT, contrôle d'accès strict (RBAC) et validation stricte des domaines cibles.
  • Persistance : Accès à PostgreSQL et archivage structuré des audits horodatés et scellés.
🧠 AIaaS Découplée — Ollama (Qwen) Port 25000 GPU
  • Modèle déployé : qwen2.5-coder:7b (GGUF Q4_K_M) accéléré par GPU sur l'hôte Windows.
  • Architecture Découplée : REST API HTTP dédiée sur port 25000 (accessible en local ou via réseau Host-Only).
  • Mode Function Calling : Prompts contraints avec sortie JSON Schema stricte sans texte parasite.
  • Résilience & Fallback : Basculement automatique sur moteur de règles déterministe en cas de déconnexion.
🎯 Sonde Autonome & Cible Probe Agent (<50Mo)
  • Cibles autorisées : Domaines étatiques (.gov.tn, .tn, .com.tn) et sandbox de test autorisées.
  • Port Scanner : Sondage asynchrone par sockets TCP purs et capture de bannières brutes.
  • Web Inspector : Audit passif SSL/TLS, analyse des en-têtes HTTP de sécurité et détection de stack.
  • PoC Verifier : Validation dynamique non destructive avec élimination totale des faux positifs.

Guide des Réponses aux Questions Techniques (« HOW? »)

Arguments techniques et protocolaires précis pour répondre à toutes les questions d'implémentation du jury lors de la soutenance :

Q1. HOW : Comment le Frontend et le Backend communiquent-ils en temps réel ?
Réponse courte : Par un modèle hybride : requêtes REST sécurisées par JWT pour le contrôle, et WebSockets bi-directionnels pour le streaming télémétrique des logs sans surcharge de polling.
L'auditeur clique sur « Lancer Audit » : Next.js envoie un POST /api/v1/audit/start avec JWT. Le backend valide la requête, génère un UUID scan_id et répond immédiatement 202 Accepted. Le frontend ouvre alors instantanément une connexion persistante wss://api.cyberscore.lan/ws/audit/{scan_id}. Le gestionnaire ConnectionManager de FastAPI pousse chaque progression (port trouvé, CVE confirmée) en JSON directement dans la timeline du navigateur.
Q2. HOW : Comment le Graphe d'Agents IA s'exécute-t-il concrètement ?
Réponse courte : Il s'agit d'une machine à états finis (StateGraph). Tous les agents partagent l'objet Pydantic AuditState et s'exécutent de façon ordonnancée.
L'Agent 1 (Reconnaissance) démarre avec l'état initial. Il invoque Nmap et met à jour open_ports et technologies. L'Agent 2 prend le relais : en lisant les technologies (ex: Apache 2.4.52), il sélectionne uniquement les templates de vulnérabilités correspondants dans Nuclei et peuple potential_cves. L'Agent 3 (Validation PoC) teste chaque CVE via le navigateur headless pour confirmer l'exploitabilité. Enfin, l'Agent 4 synthétise les failles validées et produit le plan de remédiation final.
Q3. HOW : Comment l'IA locale (Ollama/Qwen) est-elle contrainte sans fuite cloud ?
Réponse courte : Zéro appel externe. Le backend communique sur le réseau Docker interne avec Ollama via l'API /api/chat en mode Function Calling avec une température stricte de 0.1.
FastAPI envoie un prompt système strict imposant une réponse au format JSON Schema conforme à nos modèles Pydantic. La température de 0.1 élimine les hallucinations et assure un raisonnement déterministe. Aucune donnée d'audit, adresse IP ou vulnérabilité ne quitte le réseau privé du serveur RHEL 9.5.
Q4. HOW : Comment le Backend lance-t-il les conteneurs Docker de manière sécurisée ?
Réponse courte : Zéro commande bash sauvage. Le backend utilise le SDK Python Docker officiel (docker.from_env()) pour créer des conteneurs éphémères non-root bridés en ressources.
Chaque conteneur d'outil est instancié avec read_only=True (système de fichiers en lecture seule), mem_limit="512m", nano_cpus=1000000000 (1 cœur CPU max), l'utilisateur non-privilégié user="1001:1001", et la directive auto_remove=True qui garantit la destruction immédiate du conteneur dès la fin du scan.
container = client.containers.run( image="cyberscore-scanner-recon:latest", command=["nmap", "-sV", "-T3", "-F", "--unprivileged", target_host], mem_limit="512m", nano_cpus=1000000000, read_only=True, user="1001:1001", cap_drop=["ALL"], cap_add=["NET_RAW"], remove=True )
Q5. HOW : Comment la VM RHEL 9.5 empêche-t-elle une évasion de conteneur (Hardening) ?
Réponse courte : Grâce à SELinux actif en mode Enforcing, au filtrage strict de Firewalld et au remapping des utilisateurs (userns-remap).
SELinux applique le contexte mandataire container_t. Même si un binaire dans un conteneur est compromis, le noyau RHEL lui interdit formellement d'accéder au système de fichiers hôte (/etc, /root, /proc). Firewalld applique une politique DROP par défaut ne laissant ouverts que les ports strictement nécessaires (3000 pour Next.js, 8000 pour FastAPI).
Q6. HOW : Comment les rapports sont-ils certifiés avec l'empreinte SHA-256 ?
Réponse courte : Dès la fin de l'audit, le binaire PDF généré est haché par l'algorithme SHA-256 et consigné dans PostgreSQL avec un horodatage immuable.
L'empreinte cryptographique est imprimée sur la page de garde du rapport et encodée dans un QR-code de vérification. Toute tentative de modification ultérieure du contenu du document PDF produit un hash différent, prouvant immédiatement la falsification.
